The QR trick

Every table's QR points to the same menu — only the ?t=7 at the end changes. That number is how the kitchen knows which table to serve. Printing 40 QRs for 40 tables is one click.

Multi-tenant security

Every restaurant sees only its own data.

The rule (RLS)

Supabase has a feature called Row Level Security. We write one rule: "you can only touch rows where restaurant_id = your restaurant." The database itself enforces it — even if there's a bug in the app, one owner can never see another's menu or orders.

Two kinds of access

Owners log in (email/Google) and get locked to their own restaurant. Customers don't log in at all — they only get read access to a menu and can create an order. They can never edit prices or see other tables.

In plain words

It's like a shared apartment building: everyone uses the same building (one database), but your key only opens your own flat. The lock is built into the building, not the honesty of the tenants.

Your USP, technically

One menu component. Twenty themes as data.

This is why you can offer 20 designs (and grow to 100) as a solo founder. The menu is built once. Each template is just a small block of settings — colours and fonts — that gets poured into it. Adding a new template is a data entry, not a coding project.

// A template is just this — pure data, no new code:
const tandoorTheme = {
  name: "Zaika Fire",
  colors: { bg: "#FFF6E9", accent: "#E8322A", ink: "#1B1206" },
  fonts:  { display: "Anton", body: "Manrope" },
  shape:  { radius: "24px", style: "image-forward" }
}

// The SAME component renders any theme:
<Menu theme={tandoorTheme} dishes={dishes} />
// Owner picks "Zaika Fire" → their menu instantly looks like the flagship.
Why it matters

Competitors hand-build each of their 4–5 themes, so they're stuck. You built an engine. That's the moat — not any single design, but the ability to out-produce them on variety forever, for free.
